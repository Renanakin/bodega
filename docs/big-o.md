REGLA MAESTRA PARA AGENTES: LEY DE COMPLEJIDAD ASINTÓTICA Y ESCALABILIDAD (BIG O)Principio Rector: “No es tu servidor, es tu código”. La notación Big O no es una teoría académica opcional; es la única métrica predictiva válida para garantizar que el software diseñado soporte entornos de producción reales con millones de registros. Un código que funciona con 10 o 100 datos pero colapsa al crecer la entrada es un fallo de diseño.1. Jerarquía y Clasificación Obligatoria de ComplejidadTodo algoritmo propuesto por el agente debe ser evaluado y limitado según las cotas superiores asintóticas aceptadas en ingeniería de software:$O(1)$ — Tiempo Constante: El código accede directamente al recurso sin importar el tamaño de los datos (ej. acceso por clave en un diccionario/hashmap). Es el estándar de oro.$O(\log n)$ — Tiempo Logarítmico: El conjunto de datos se divide a la mitad en cada paso (ej. Búsqueda Binaria). Altamente eficiente para colecciones ordenadas.$O(n)$ — Tiempo Lineal: El costo crece de forma directamente proporcional al tamaño de la entrada (ej. un bucle simple recorriendo una lista). Aceptable para operaciones inevitables.$O(n \log n)$ — Tiempo Log-Lineal: Típico de algoritmos de ordenamiento eficientes (como Quicksort o Mergesort).$O(n^2)$ o superior — Tiempo Cuadrático/Exponencial (ZONA ROJA): Prohibido. Corresponde a bucles anidados u operaciones donde cada elemento interactúa con todos los demás. Cualquier propuesta que introduzca bucles anidados sobre entradas dinámicas sin justificación estricta será rechazada automáticamente.2. Directrices de Selección de Estructuras de DatosEl costo operativo de cualquier función depende directamente de la estructura elegida. El agente debe aplicar obligatoriamente:Listas/Arrays desordenados: Exigen recorridos lineales $O(n)$ para búsquedas. Usar solo cuando el orden de inserción sea el único propósito o el volumen sea irrelevante y acotado.Tablas Hash / Diccionarios: Obligatorios para búsquedas, mapeos y validaciones de existencia en tiempo constante $O(1)$.Árboles e Índices: Requeridos para mantener elementos ordenados o evitar escaneos completos de tablas en bases de datos ($O(\log n)$).3. Protocolo de Auditoría y Code Review para el AgenteAntes de generar o aprobar cualquier bloque de código, el agente debe ejecutar internamente el siguiente checklist:Identificar el peor caso: Evaluar siempre el comportamiento del algoritmo ante el peor escenario posible de entradas masivas.Justificación Explícita: Declarar de forma obligatoria la complejidad temporal ($T(n)$) y espacial ($S(n)$) estimada de la solución antes de presentarla.Refactorización Preventiva: Si se detecta un cuello de botella potencial (como un bucle dentro de otro bucle), el agente tiene la orden estricta de rediseñar la lógica utilizando estructuras de datos óptimas antes de entregar la respuesta a Renato.
